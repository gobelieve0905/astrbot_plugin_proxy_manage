# 代理管理中心：最终产品定义与架构约束

状态：规范性文档

最后更新：2026-10-09

适用范围：产品设计、架构、开发、测试、部署、文档和发布

## 1. 文档地位

本文定义代理管理中心的最终产品形态，是后续优化和修改的最高优先级依据。

- 实现、页面、测试和运维方案必须服务于本文目标，不能把“管理节点列表”误当成产品完成。
- 当前代码与本文冲突时，以本文为目标，以当前代码为待迁移实现；不得为了迁就旧实现而缩小产品目标。
- 任何会改变产品边界、流量范围、内核抽象、安全模型或失败策略的修改，必须获得产品所有者明确确认，先更新本文并说明理由，再修改代码；不得以迁就现有实现、减少工作量或单一内核限制为由自行降低目标。
- README、用户指南、CHANGELOG 和页面不得宣称尚未满足验收标准的能力已经完成。
- 本文不等同于当前版本功能说明。0.4.2 已实现插件自管 Mihomo、sing-box 与 Xray 适配器、统一适配器契约、AstrBot 默认全局出口接入，以及飞书/Telegram 官方兼容层。第三方插件和 MCP 不再需要专用接入协议；只要请求进入统一代理入口，就按目标网址规则处理，绕过入口的请求仍需单独识别和说明。

## 2. 一句话定义

代理管理中心是 AstrBot 的统一出站流量控制面：插件自行准备并管理所需代理内核，对机器人平台、Agent 推理、工具、插件、下载及相关服务产生的实际外部流量进行路由、代理、直连、失败关闭、观测和验证。

它不是：

- 只维护订阅、节点和延迟数据的面板；
- 只管理 GitHub 下载的代理开关；
- 要求用户预先部署 Mihomo、Clash、Xray、sing-box 或其他代理服务的控制器；
- 把配置“生成成功”当成真实流量“已经接管”的工具。

## 3. 不可偏离的产品不变量

### 3.1 插件拥有运行内核

普通用户安装插件前不需要在服务器、容器或宿主机预装任何代理内核。

插件负责：

1. 检测操作系统、CPU 架构、运行权限和可执行目录；
2. 获取、校验、安装、启动、监督、停止和升级内核；
3. 保存内核版本、制品来源和摘要；
4. 生成并持久化运行配置；
5. 在 AstrBot 或内核重启后恢复最后一次已验证配置；
6. 在失败时保留或恢复上一份已验证配置；
7. 向用户报告“未安装、下载失败、校验失败、不可执行、启动失败、运行异常、配置不一致”等真实状态。

用户不应被要求填写控制接口地址、监听地址、控制密钥、容器名或服务器路径。这些属于插件内部运行状态。

受 AstrBot 插件市场包体积限制，原生内核可以在首次使用时按平台从官方发布源下载；必须使用随插件发布的固定版本清单和强摘要进行校验。必须同时提供经过相同校验的离线上传入口，不能把不受信任的第三方下载镜像设为静默默认值。

### 3.2 内核可插拔，不绑定 Mihomo

“代理内核”是能力接口，不是 Mihomo 的别名。任何业务模型、节点模型、页面字段和持久化格式都不得以某个内核的专用字段作为唯一真相。

产品参考两类成熟设计：

- [Clash Verge Rev](https://github.com/clash-verge-rev/clash-verge-rev)：应用拥有并监督代理内核、配置、规则和本地出口；
- [v2rayN](https://github.com/2dust/v2rayN) 及其[支持的内核列表](https://github.com/2dust/v2rayN/wiki/List-of-supported-cores)：统一管理 Xray、sing-box、Mihomo 及其他核心，并按不同协议和配置能力选择执行核心。

首批应评估的适配器包括但不限于：

- Mihomo：适合 Clash 配置、规则、代理组和 provider 生态；
- sing-box：适合广泛协议和跨平台统一配置；
- Xray-core：适合 VMess、VLESS、Trojan、Shadowsocks 等 V2Ray/Xray 生态；
- 后续独立核心：Hysteria、TUIC、NaiveProxy 等，仅在通用适配器不能可靠覆盖且有明确需求时加入。

是否支持某协议必须由“规范化参数能否无损表达 + 适配器能否生成有效配置 + 真实运行验证是否通过”共同决定，不能只根据 URI scheme 宣称支持。

### 3.3 管理真实流量，不只管理配置

下列外部流量都属于产品范围：

- 飞书、Lark、Telegram、Discord 等机器人平台的 API、WebSocket、媒体上传和下载；
- LLM、Embedding、Rerank、TTS、STT、图像生成等 Provider；
- Agent 浏览网页、下载文件、调用第三方 API 和执行联网工具；
- AstrBot 插件产生的、且进入统一代理入口的 HTTP、HTTPS、WebSocket 及其他外部连接；
- Agent 调用 MCP 后，由 MCP 服务继续产生的外部请求；
- GitHub、插件市场、插件安装、更新、PyPI 和其他依赖下载；
- AstrBot 遥测或其他后台外部请求。

以下内部通信可以不经过外部代理出口，但必须明确列入内部直连清单：

- 回环地址和 AstrBot Dashboard；
- AstrBot 与本机或同一可信网络内 MCP 的内部调用；
- 插件与自管内核的控制连接；
- 受限运维通道、Unix Socket 和健康检查。

MCP 收到内部调用后访问外部服务的流量，只有在请求进入统一代理入口时才会按网址规则管理。插件或 MCP 自行建立的独立网络、原生 socket、QUIC、独立进程/容器出口和显式绕过环境代理的客户端不属于统一入口范围，不能被网址规则拦截。

AstrBot 核心、Provider 和平台适配器由代理管理插件维护内置兼容层。第三方插件和 MCP 不需要声明或实现代理管理中心专用协议；用户只需让其请求使用统一 HTTP/HTTPS（必要时 SOCKS）入口，并通过网址/IP 规则指定代理组。这里的内置兼容层只服务 AstrBot 自身已确认的官方客户端路径，不向第三方插件暴露适配 API。

### 3.4 DIRECT 也是受管理策略

外部域名不能因为配置在 `no_proxy` 中而脱离管理。飞书、Telegram 或模型平台即使选择直连，也应先进入统一出口，再由明确的 `DIRECT` 规则决定。

`no_proxy` 只用于回环、可信内部服务和控制面通信。任何外部流量的直连都必须：

- 有明确规则；
- 有命中记录；
- 能被预览和验证；
- 能在用户选择失败关闭时禁止回退。

### 3.5 不允许静默旁路

产品必须区分两种覆盖等级：

#### 标准接管

插件配置 AstrBot 的稳定本地 HTTP/SOCKS 入口，并让需要代理的请求经过该入口。它适用于无需宿主机特权的普通安装；第三方插件和 MCP 是否使用该入口由其自身客户端配置决定。

#### 强制接管

在用户运行环境允许时，通过容器网络策略或宿主机出口规则禁止 AstrBot 和相关服务绕过插件出口直接访问公网。强制接管需要额外系统权限时，必须明确说明并由管理员启用。

普通插件权限无法拦截任意第三方原生扩展、裸 socket、显式 `trust_env=false` 客户端或其他容器的全部数据包。标准接管模式必须说明统一入口只能管理进入其中的请求；`NO_PROXY`、自带 `proxy`/`proxies`、独立网络和特殊传输都可能绕过网址规则。

## 4. 最终用户体验

### 4.1 首次安装

1. 用户从 AstrBot 插件市场或仓库安装插件；
2. 插件检测运行平台和可用适配器；
3. 插件准备默认内核，或提示用户从受支持内核中选择；
4. 插件从官方源获取固定制品并校验，或接受离线制品；
5. 插件启动仅本机或受限内部网络可访问的控制接口和统一出口；
6. 用户导入订阅、配置文件或单个节点；
7. 插件展示解析、协议覆盖、所需内核和不支持项；
8. 插件生成安全默认策略；
9. 插件将 AstrBot 全局代理指向稳定入口；
10. 若已有 Provider 或平台客户端需要重建，页面明确提示并引导完成一次 AstrBot 重启；
11. 实际出站验证通过后，状态才显示“已接管”。

首次安装的受限引导通道：当没有通过固定清单校验的插件自管内核、且没有正在运行的自管内核时，页面必须展示系统/CPU 架构、安装指引及离线上传入口。用户主动选择“受限直连安装”后，只允许固定清单内核制品通过独立客户端直连官方 HTTPS 源及其受信制品分发域名；每次重定向检查域名、HTTPS 和公网地址，保留超时、体积上限及 SHA-256 校验。该通道不改变 AstrBot 的业务代理环境，不供订阅、更新检查或任意 URL 使用；已有可用内核时，内核下载只走稳定入口，故障时不得回退直连。普通服务器上预装但未经插件校验的内核不视为可信自管资源。

业务环境可以提前指向尚未就绪的稳定入口以保持失败关闭；页面必须说明内核和规则未就绪时业务联网不可用，不能把此时的入口配置标记为流量已接管。

没有订阅或节点时，插件可以运行在“受管理直连”模式，但不得伪装成已有代理节点。

### 4.2 日常使用

用户主要操作对象是“流量策略”，不是内核 YAML：

- 哪类 AstrBot 流量；
- 命中哪些域名或 IP；
- 选择哪个出口组；
- 允许直连、必须代理还是失败关闭；
- 当前实际选择、健康状态和最近验证结果。

高级页面才展示内核、生成配置和调试信息。普通页面不得要求用户理解内核专有术语。

## 5. 规范化数据模型

插件持久化的是与内核无关的规范化模型，而不是某种内核配置文件的反序列化副本。

### 5.1 订阅

至少支持：

- Clash/Mihomo YAML；
- 常见 Base64 URI 列表；
- VMess、VLESS、Trojan、Shadowsocks、SOCKS、HTTP、Hysteria2、TUIC、AnyTLS 等单节点链接；
- sing-box 或其他结构化配置的受控导入；
- 多订阅、刷新、差异、别名和失效引用。

导入器必须保留未知字段和原始来源，不能为了适配当前默认内核而丢弃其他内核需要的参数。任何脚本型订阅或不可信可执行转换默认禁止。

### 5.2 节点

节点至少分离：

- 稳定身份；
- 用户显示名称与来源名称；
- 协议及完整连接参数；
- 订阅来源；
- 支持它的内核适配器集合；
- 当前执行内核；
- 用户启用、排除和别名状态；
- 参数修订、健康状态和最后验证时间。

稳定身份必须包含区分真实连接所需的字段。相同服务器和主体、但 SNI、传输层、路径或安全参数不同的节点不能碰撞。

### 5.3 流量策略

策略至少支持：

- 流量类别；
- 域名精确、域名后缀和必要的 IP/CIDR 匹配；
- 优先级和稳定顺序；
- 目标出口组；
- 直连、代理、拒绝和失败关闭；
- 命中与验证记录。

当前不按第三方插件或 MCP 身份分流。同一目标域名/IP 由不同来源访问时命中相同规则；内核不支持的规则必须在应用前明确提示，不能静默忽略。

## 6. 内核适配器契约

每个内核通过统一接口接入，至少提供：

1. `capabilities`：协议、规则、代理组、测速、热重载、运行核对和平台支持；
2. `artifact`：受支持系统、架构、官方制品、版本和摘要；
3. `render`：从规范化模型生成候选配置；
4. `validate`：离线校验候选配置；
5. `start` / `stop` / `restart`：受监督的进程生命周期；
6. `apply` / `rollback`：持久化应用与恢复；
7. `inspect`：读取实际运行状态；
8. `select`：切换可选代理组；
9. `probe`：对节点和统一入口进行受控检测；
10. `verify`：核对运行配置和实际流量；
11. `redact`：为页面、日志和诊断生成脱敏视图。

业务层不得直接拼接 Mihomo、sing-box 或 Xray 专用配置。所有专用转换必须位于对应适配器内。

## 7. 多内核编排

AstrBot 始终只使用一个稳定的插件入口。底层可以运行一个或多个插件拥有的内核：

- 单个内核能覆盖当前节点和策略时，优先使用单内核；
- 不同协议需要不同内核时，由编排层启动辅助内核；
- 主路由内核可以把某些出口转发到辅助内核暴露的本地 SOCKS/HTTP 端口；
- 辅助端口只监听回环或插件私有网络，并使用随机凭据或网络隔离；
- 用户切换内核时，稳定入口地址不变；
- 内核崩溃不得导致未授权直连。

内核选择应基于能力和已验证兼容性。不能因为某个内核是当前默认值，就把其他协议错误标记为永久不支持。

## 8. 流量接入层

插件必须维护一份“流量接入清单”，覆盖 AstrBot 当前版本中的：

- 全局 `http_proxy`、`https_proxy`、必要时的 `all_proxy`；
- Provider 的独立 `proxy` 配置；
- 平台 SDK 的 HTTP 和 WebSocket 代理能力；
- 进入统一入口的公共 HTTP 客户端和插件网络访问接口；
- 未进入统一入口的自建客户端、原生 socket、独立进程/容器和特殊传输（作为旁路风险记录）；
- 更新和下载组件。

每项必须记录：接入方式、是否需要重启、能否强制、实际验证方法和当前状态。AstrBot 版本升级后必须重新执行流量接入回归。

## 9. 安全、隐私与供应链

- 内核和资源只使用固定版本；禁止静默跟随 `latest`；
- 下载后必须验证随插件发布的强摘要；有签名时同时验证签名；
- 下载镜像只能改变传输来源，不能改变预期摘要；
- 子进程不得通过 Shell 拼接用户输入；
- 控制接口默认仅回环可达，并使用随机密钥；
- 节点凭据、订阅地址、控制密钥和带认证入口不得出现在页面状态、事件或普通日志；
- 配置、备份、运行状态和制品目录使用最小权限；
- 实际验证不得携带模型、平台或业务 Token；
- 默认不关闭 TLS 验证。节点协议确需特殊证书策略时，必须逐节点显示风险；
- 插件不提供公共代理、不开放公网控制端口、不作为任意 URL 转发服务。

## 10. 配置事务和恢复

每次应用必须完成：

1. 生成候选；
2. 规范化模型校验；
3. 内核适配器离线校验；
4. 创建私有备份；
5. 原子写入持久配置；
6. 热重载或受控重启；
7. 核对节点、组、规则、入口和实际选择；
8. 通过统一入口发起无业务凭据的真实请求；
9. 记录已保存和已应用修订；
10. 任一步失败时恢复上一份配置并重新核对。

只改变内存、不写入持久配置的操作不能标记为“已应用”。只检查控制 API 存活不能标记为“流量已接管”。

## 11. 可观测性

页面应能回答：

- 哪些 AstrBot 流量已接管；
- 哪些流量明确直连；
- 哪些请求入口尚未接入或无法判定；
- 请求命中了哪条规则、哪个出口组和哪个节点；
- 当前出口是否与用户策略一致；
- 最近一次配置应用、节点检测和实际出口验证何时发生；
- 是否存在旁路、运行配置漂移或恢复失败。

日志和历史记录必须有容量上限、轮转和保留策略。节点健康、任务和事件不得无限增长。

## 12. 最终验收标准

版本只有同时满足以下条件，才能宣称达到最终产品形态：

1. 在没有预装任何代理内核的受支持环境中完成安装；
2. 插件能够安全准备并监督至少一个内核；
3. 至少两个不同内核适配器通过相同契约和测试；
4. 支持矩阵中的订阅和节点参数能够无损导入、保存、刷新和迁移；
5. 机器人平台、模型 Provider、Agent 工具、插件下载和统一入口中的请求完成真实网址分流验证；第三方插件与 MCP 仅在使用统一入口时纳入同一验证；
6. `DIRECT`、指定节点、自动组、拒绝和失败关闭均有实际流量测试；
7. 代理或内核故障时不存在静默直连；
8. AstrBot、插件和内核分别重启后，配置和流量策略保持一致；
9. 页面报告与实际运行状态一致；
10. 凭据脱敏、文件权限、制品校验和回滚测试通过；
11. 前端、规范化模型、每个内核适配器和真实 AstrBot 环境均有自动化回归；
12. 当前版本的支持范围、限制和未接入项被准确记录。

## 13. 明确的非目标

- 不管理与 AstrBot 无关的整台服务器流量；
- 不把服务器变成公共代理或 VPN 服务；
- 不自动导入、信任或执行订阅提供的脚本；
- 不为了“节点可用”而关闭目标网站 TLS 验证；
- 不在用户不知情时修改宿主机防火墙、系统代理或网络接口；
- 不用虚假成功、旧健康状态或配置生成结果代替真实流量验证。

## 14. 开发治理

后续每轮修改必须回答：

1. 它改善了哪一类 AstrBot 实际流量？
2. 它修改了规范化模型、哪个内核适配器或哪个流量接入点？
3. 它是否引入内核专用假设；若有，是否被限制在适配器内部？
